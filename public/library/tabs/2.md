# Build Guidance Document  

Build Guidance Document

(Procedia)

  
  

Audience: Ashley + Cursor

Purpose: Prevent confusion, over-engineering, and paralysis. Enforce forward progress.

  
  

\---

  

1\. What This Project Is

  

This is a Single-Page Application (SPA) built primarily through AI assistance (Cursor).

  

Ashley does not hand-code features.

Cursor generates code.

The system must be safe, reversible, and understandable at a conceptual level.

  
  

\---

  

2\. Core Stack (Locked Decisions)

  

These decisions are final unless explicitly changed later.

  

Frontend: SPA (Vite + TypeScript)

  

Backend: Supabase (Auth, Database, RLS)

  

Language: TypeScript (for safety, not for manual coding)

  

Version Control: Git + GitHub (private repo)

  

AI Services: OpenAI API (feature-gated)

  

Deployment: Later (not a current concern)

  
  

Cursor must respect this stack and not introduce alternatives without permission.

  
  

\---

  

3\. Guiding Principles (Non-Negotiable)

  

3.1 Vertical Slice First

  

Work is done in small, complete vertical slices, not broad systems.

  

A slice must:

  

touch auth

  

touch database

  

touch UI

  

prove RLS works

  

visibly “do something”

  
  

No partial systems.

  
  

\---

  

3.2 One Ticket at a Time

  

Cursor is always given one build ticket.

  

Rules:

  

Implement only what the ticket asks

  

Do not refactor unrelated code

  

Do not add “helpful extras”

  

Stop when the ticket is complete

  
  
  

\---

  

3.3 Safety Over Cleverness

  

Prefer boring, explicit solutions

  

Avoid abstractions early

  

Avoid “future-proofing”

  

Avoid magic

  
  

Clarity \> elegance.

  
  

\---

  

4\. TypeScript Policy (Important)

  

Ashley does not need to understand TypeScript.

  

TypeScript exists to:

  

prevent Cursor hallucinations

  

define data shapes

  

surface errors early

  

improve autocomplete and self-correction

  
  

If TypeScript errors appear:

  

Cursor must fix them

  

Ashley does not debug them manually

  
  
  

\---

  

5\. Database Rules

  

5.1 Migrations

  

All schema and RLS changes happen via migrations

  

Old migrations are never edited

  

Each migration does one thing

  
  

Each migration includes:

  

forward change

  

rollback comment (manual if needed)

  
  
  

\---

  

5.2 RLS (Row Level Security)

  

RLS is ON by default

  

Start with “deny all”

  

Add policies intentionally

  

Test with real auth contexts

  
  

Security correctness matters more than speed.

  
  

\---

  

6\. Environments

  

The system will have:

  

local

  

staging

  

production (later)

  
  

Risky changes go to staging first.

Production is never used for experimentation.

  
  

\---

  

7\. Git & GitHub Rules

  

Everything lives in Git

  

Small, descriptive commits

  

Git history is the source of truth

  
  

Ashley does not need Git mastery.

Git exists to prevent irreversible mistakes.

  
  

\---

  

8\. Automation & Boring Checks

  

The project will include:

  

formatting

  

linting

  

type checking

  

basic tests

  

CI checks

  
  

These define “done” objectively:

  

\> If checks pass, the work is acceptable.

  
  
  
  

\---

  

9\. API & AI Usage

  

APIs are boundaries, not magic

  

AI features are optional and gated

  

UI should work without AI first

  

AI is plugged in later, behind switches

  
  

Cost control and safety matter.

  
  

\---

  

10\. Documentation Philosophy

  

Documents are constraints, not essays.

  

Good docs:

  

are short

  

are concrete

  

tell Cursor what not to do

  

define rules and boundaries

  
  

Bad docs:

  

are speculative

  

are philosophical

  

describe imaginary future systems

  
  
  

\---

  

11\. Success Criteria

  

Progress is measured by:

  

working features

  

applied migrations

  

passing checks

  

visible screens

  
  

Not by:

  

document length

  

architectural completeness

  

theoretical elegance

  
  
  

\---

  

12\. Default Instruction to Cursor

  

When in doubt, Cursor should:

  

1\. Ask for clarification

  
  

2\. Choose the simplest option

  
  

3\. Implement the smallest slice

  
  

4\. Stop early rather than overbuild

  
  
  
  

\---

  

13\. Current Focus

  

The immediate goal is Ticket 001:

  

\> Auth → Person row → RLS → Simple dashboard

  
  
  

Everything else is secondary.

  
  

\---

  

Final Note

  

Ashley is not “behind.”

Ashley is building correctly for a non-coder using AI.

  

This document exists so thinking stops and building begins.
