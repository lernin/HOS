# **📄 White Paper**

## **Adaptive Display Management System (ADMS) v3.0**

*A device-anchored, window-scoped system for seamless multi-display control*

---

## **1\. Abstract**

This system enables users to **connect, control, and manage shared displays** using short-lived codes, without requiring heavy authentication or fragile UI flows.

The core innovation is a clean separation of:

* **Devices** (persistent hardware/browser presence)  
* **Displays** (stable, named screen targets)  
* **Sessions** (temporary interaction states)  
* **Windows** (true UI control units)  
* **Connection Codes** (ephemeral invitations)

👉 The breakthrough:

A **browser window—not a tab—is the unit of display control**

---

## **2\. Core Problem**

We need:

* Multiple displays per device  
* Multiple users interacting simultaneously  
* Seamless phone → screen control  
* Zero-friction entry (no forced login)  
* Clean mental model (no “what is happening??” moments)

Most systems fail because they:

❌ Mix device \+ session \+ display  
 ❌ Treat tabs independently  
 ❌ Recreate displays repeatedly  
 ❌ Overcomplicate identity

---

## **3\. System Model**

---

### **3.1 Device (Persistent)**

A real machine or browser host.

device  
\- id  
\- label (optional)  
\- last\_seen\_at

👉 Example: Ashley’s desktop, a classroom PC

---

### **3.2 Display (Stable, Device-Bound)**

A named virtual screen attached to a device.

display  
\- id  
\- device\_id  
\- name ("Upper", "Widescreen")  
\- position\_hint (optional)

✔ Displays persist  
 ✔ Displays do NOT get recreated on connection

---

### **3.3 Display Session (Ephemeral)**

A temporary interaction layer.

display\_session  
\- id  
\- display\_id  
\- session\_code  
\- status ("waiting" | "active")  
\- controller\_person\_id  
\- expires\_at

👉 This is what the QR / code connects to

---

### **3.4 Connection Code (Universal Entry)**

connection\_codes  
\- code (6-digit)  
\- purpose ("display\_join", "person\_connection", "recovery")  
\- target\_id  
\- expires\_at

✔ One system  
 ✔ Multiple uses

---

## **4\. Core Principles**

---

### **4.1 Device is the anchor**

You always connect to a **device context first**

---

### **4.2 Displays are stable**

“Upper screen” remains “Upper screen” forever

---

### **4.3 Sessions are temporary**

* Codes expire  
* Sessions reset  
* Displays persist

---

### **4.4 Codes are invitations—not identity**

They allow access, not authority.

---

### **4.5 Window is the unit of control ⭐**

This is the most important rule in the system

---

## **5\. Window-Scoped Display Model (Critical)**

---

### **5.1 Core Rule**

window\_id → display\_id

NOT:

tab\_id → display\_id ❌

---

### **5.2 Definition**

A **browser window**:

* owns the display assignment  
* controls all tabs inside it  
* acts as the UI control boundary

---

### **5.3 Behavior**

#### **When user changes display (pencil icon):**

👉 ALL tabs in that window update instantly

---

### **5.4 Example (your exact case)**

* Window has 5 tabs  
* You’re on tab \#2  
* You rename display → “Upper”

✅ Result:

All 5 tabs show:

\[Upper\]

---

### **5.5 Sync Mechanism**

Each tab shares:

window\_id (shared)  
tab\_id (unique)  
display\_id (inherited)

Sync via:

* `BroadcastChannel` (primary)  
* `localStorage` events (fallback)

---

### **5.6 Required Flow**

User updates display  
→ update window state  
→ broadcast to all tabs  
→ all tabs update UI  
→ optional DB sync

---

### **5.7 Tab Behavior**

| Action | Result |
| ----- | ----- |
| New tab | inherits window display |
| Tab click | no change |
| Tab rename display | updates all tabs |

---

### **5.8 Window Split (Important)**

When a tab is dragged out:

→ new window\_id created  
→ keeps previous display initially  
→ becomes independently controllable

---

### **5.9 Multiple windows**

Even on same monitor:

Window A → Upper    
Window B → Widescreen 

✔ Fully independent

---

## **6\. Connection Flow (Simple \+ Clean)**

---

### **Step 1 — Device shows code**

User opens hand panel:

→ create display\_session  
→ generate code (e.g. 837104\)

---

### **Step 2 — User scans or types code**

Phone or another device:

→ resolve connection\_code  
→ find display\_session  
→ find device

---

### **Step 3 — Display selection**

1 display → auto-connect    
multiple → choose display 

---

### **Step 4 — Session activates**

display\_session.status \= active  
controller\_person\_id \= user

---

### **Step 5 — Desktop reacts**

window sees active session  
→ enters display mode

---

## **8\. Facilitator vs Participant**

---

### **Facilitator**

* opens display sessions  
* controls screens  
* invites participants

---

### **Participant**

* joins session  
* interacts within limits

---

### **Entry types**

| Entry | Meaning |
| ----- | ----- |
| QR scan | connect to display |
| Code entry | same |
| Invite | participant join |

## **11\. Key Design Decisions**

---

✔ Window owns display  
 ✔ Tabs never act independently  
 ✔ Displays are persistent  
 ✔ Sessions are temporary  
 ✔ Codes are universal  
 ✔ Devices are entry points

---

## **12\. Anti-Patterns (Avoid These)**

---

❌ Creating display on every scan  
 ❌ Tracking tabs individually  
 ❌ Mixing session \+ display  
 ❌ Persistent codes  
 ❌ UI-driven DB chaos
