# Taxonym implementation  

**The Taxonym System**

*A Multi-Dimensional Structure for Representing Concepts, Reality, and Perception*

## **1. Overview**

The **Taxonym** is a unified system for organizing knowledge as a **single multi-dimensional tree**.

It integrates:

  - **Concepts (classes)**
  - **Instances (real-world objects)**
  - **Attributes (properties)**
  - **Perceptions (summaries)**
  - **History (logs)**

Rather than separating ontology, data, and analytics, the Taxonym keeps everything **aligned within one structure**.

## **2. Core Principle**

**All knowledge exists in one structure, expressed across different dimensions.**

These dimensions are:

|  |  |
| :-: | :-: |
| \*\*Dimension\*\* | \*\*Meaning\*\* |
| Eidonym | What something \*is\* (class) |
| Idionym | What \*exists\* (instance) |
| Attribute | What something \*has\* |
| Summary | What is \*typically observed\* |
| Log | What has \*changed over time\* |

## **3. System Structure**

TAXONYM

├── EIDONYM (class layer)

│   ├── Eidonym

│   ├── Eidonym\_Log

│   ├── Eidonym\_Attribute

│   ├── Eidonym\_Attribute\_Log

│   ├── Eidonym\_Attribute\_Summary

│   └── Eidonym\_Attribute\_Summary\_Log

│

└── IDIONYM (instance layer)

    ├── Idionym

    ├── Idionym\_Log

    ├── Idionym\_Attribute

    └── Idionym\_Attribute\_Log

  

## **4. Eidonym Layer (Conceptual)**

The **Eidonym layer** defines what is generally true about a category.

### **Eidonym**

Represents a class:

  - Dog
  - Car
  - Human

### **Eidonym\_Attribute**

Defines possible attributes:

  - Dog → legs
  - Car → color
  - Human → height

### **Eidonym\_Attribute\_Summary**

Represents **observed distributions**:

  - Cars → mostly white and black
  - Humans → height distribution

This is not truth. It is a **snapshot of perceived reality**.

### **Logs**

Track all changes to:

  - classes
  - attributes
  - summaries

## **5. Idionym Layer (Instance)**

The **Idionym layer** captures real-world data.

### **Idionym**

Represents a specific instance:

  - Fido
  - Ashley’s car

### **Idionym\_Attribute**

Stores actual values:

  - Fido → legs = 3
  - Car → color = blue

This is the **source of truth**.

### **Logs**

Track:

  - creation
  - updates
  - deletions

## **6. Key Distinction**

|  |  |
| :-: | :-: |
| \*\*Layer\*\* | \*\*Role\*\* |
| Eidonym | Defines possibility |
| Idionym | Records reality |
| Summary | Describes typical patterns |
| Log | Records history |

## **7. Perception vs Reality**

A critical design principle:

**Summaries do not overwrite truth.**

  - **Truth** = Idionym\_Attribute
  - **Perception** = Eidonym\_Attribute\_Summary
  - **History** = Logs

Summaries are:

  - approximate
  - time-bound
  - useful but not authoritative

## **8. Distribution Types**

The system supports different real-world patterns:

  - **Normal (bell curve)** → height
  - **Long-tail distribution** → car colors
  - **Uniform** → rare cases

The system does not enforce distribution type — it simply **records observed patterns**.

## **9. Minimal Summary Model (MVP)**

Eidonym\_Attribute\_Summary

\- eidonym\_id

\- attribute\_id

\- value

\- percentage

\- source (optional)

\- timestamp

  

This keeps the system:

  - simple
  - fast
  - practical

## **10. Why This System Works**

The Taxonym avoids common failures:

❌ Mixing class and instance  
 ❌ Treating averages as truth  
 ❌ Losing historical changes  
 ❌ Hardcoding assumptions

Instead, it provides:

✅ Clear separation of concerns  
 ✅ Support for exceptions  
 ✅ Built-in perception layer  
 ✅ Full historical traceability

## **11. Build Order (Recommended)**

1.  Eidonym
2.  Idionym
3.  Eidonym\_Attribute
4.  Idionym\_Attribute
5.  Logs
6.  Summary (last)

Do not start with summaries.
