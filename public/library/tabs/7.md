# **security.md** **(Procedia)**

## **Procedia — Security & Quality Guardrails (MVP)**

**Owner:** Ashley  
 **Status:** MVP-level, intentionally lightweight  
 **Purpose:** Prevent data leaks, role abuse, and silent failures — without slowing development

This document is **not** an expansion of the architecture.  
 It exists to answer one question:

*“How do we make sure this doesn’t quietly break, leak data, or scare parents?”*

## **1. Security Philosophy (Plain English)**

Procedia is **not a bank** and **not a medical system**.  
 However, it **does involve children**, so we follow these principles:

  - Don’t store sensitive family data longer than necessary  
      
  - Don’t let people see things they shouldn’t  
      
  - Make mistakes recoverable  
      
  - Prefer simple rules over clever systems  
      
  - Detect problems early instead of perfectly preventing them  
      

If something feels complicated, we **simplify**, not harden.

## **2. Data Minimization (Very Important)**

### **What we DO store**

  - Person IDs and display names  
      
  - Organization relationships  
      
  - Family *relationships* (who is connected to whom)  
      
  - Learning content and progress  
      
  - Audit logs of privileged actions  
      

### **What we DO NOT persist globally**

  - Family home addresses  
      
  - Phone numbers  
      
  - Emails for entire families across schools  
      

### **Rule**

Family *identity* can persist, but **family personal data is entered per-organization, per-school**, at signup time.

That means:

  - Parents re-enter details when joining a new school  
      
  - Schools only see what parents explicitly provide *to that school**  
      
    *
  - A breach at one school does **not** expose lifetime family history  
      

This dramatically reduces breach impact.

## **3. Core Security Boundary (The Only One That Matters)**

**Organizations are the security boundary.**

Rules:

  - No data crosses organizations  
      
  - No queries span multiple organizations  
      
  - Family visibility is scoped to the organization where the child is enrolled  
      
  - Staff belong to exactly **one** organization (MVP)  
      

If this rule holds, everything else becomes manageable.

## **4. Row Level Security (RLS): MVP Intent**

RLS is used for **data isolation**, not fancy logic.

### **Global Rules**

  - A person can always see their own records  
      
  - Shared visibility only exists inside the same organization  
      
  - Creation is more permissive than updates  
      
  - Deletion is almost always soft-delete  
      

### **Non-Negotiable RLS Tests**

These must exist before MVP launch:

1.  A teacher **cannot** see students from another school  
      
2.  A parent **cannot** see children outside their family group  
      
3.  A staff member **cannot** escalate their own role  
      
4.  A connect code **cannot** be reused after expiry  
      

If these pass, the system is safe enough for MVP.

## **5. Connect Codes (Practical, Not Paranoid)**

Connect codes are **coordination tools**, not secrets.

MVP defaults:

  - Numeric only  
      
  - Time-limited (minutes to hours, depending on purpose)  
      
  - Single-use by default  
      
  - Purpose-scoped (guardian link, teacher claim, org invite)  
      

Rules:

  - A connect code never grants authority immediately  
      
  - Every use creates a *pending* object  
      
  - Confirmation is always required for power  
      

This prevents accidental or malicious privilege escalation.

## **6. Testing Strategy (Small but Effective)**

Testing exists to answer:

“If this breaks, will we notice?”

### **Required Test Layers (MVP)**

#### **1. Database Tests**

For each core table:

  - Valid insert works  
      
  - Invalid insert fails  
      
  - Foreign keys enforce correctly  
      
  - Soft delete works  
      

#### **2. RLS Boundary Tests (Critical)**

  - Cross-organization access fails  
      
  - Self-access works  
      
  - Staff vs parent vs student visibility behaves correctly  
      

#### **3. Critical Flow Tests**

Only these flows **must** be tested end-to-end:

  - School nomination → teacher confirmation → searchable org  
      
  - Family creation + sibling addition  
      
  - Connect code generation → use → expiration  
      
  - Tool grant → dashboard visibility  
      

That’s it. No massive test suite.

## **7. Logging & Auditing (MVP Level)**

We log **only privileged actions**:

  - Tool grants / revokes  
      
  - Organization confirmations  
      
  - Staff membership changes  
      
  - Family relationship changes  
      
  - Role claims  
      

MVP approach:

  - Write to audit\_log  
      
  - Also console.log during development  
      
  - Never silently fail privileged actions  
      

No analytics dashboards yet. Visibility beats elegance.

## **8. Rate Limiting & Abuse Prevention**

MVP safeguards:

  - Soft caps (e.g., nominations per learner)  
      
  - Rate limits on connect code creation  
      
  - Automatic cooldowns on suspicious behavior  
      

No automated bans.  
 Escalation = visibility + manual review.

## **9. What This Document Is** ***Not***

This document does **not**:

  - Add complexity to the architecture  
      
  - Require enterprise security tooling  
      
  - Mandate perfect coverage  
      
  - Block development progress  
      

Its job is to **reduce fear**, not increase it.
