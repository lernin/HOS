# **Display Inference and Identification Model**

## **1\. Introduction**

Modern web applications operate in environments where direct access to hardware-level display configuration is restricted for privacy and security reasons. As a result, applications cannot reliably enumerate or identify all physical displays connected to a device.

This document outlines a pragmatic approach to **inferring and stabilizing display identity over time** using observable browser-level data. The goal is to provide a low-friction, scalable system for recognizing and managing displays without requiring explicit user configuration in most cases.

---

## **2\. Problem Definition**

The system must:

* Identify distinct displays used by a device  
* Maintain stability of display identity over time  
* Avoid excessive user prompts or configuration burden  
* Support multi-display environments when present  
* Operate under browser-imposed limitations

Constraints:

* No access to full monitor layout (position, count, topology)  
* No persistent hardware identifiers  
* Display characteristics may vary slightly due to OS/UI changes

---

## **3\. Core Concept**

Displays are not explicitly created or declared by users.

Instead, displays are:

> **Inferred entities derived from repeated observation of browser-reported screen characteristics**

This shifts the model from:

explicit configuration → system truth

to:

observed behavior → inferred truth

---

## **4\. Display Fingerprint**

Each display is identified using a minimal, stable fingerprint:

* `screen_width`  
* `screen_height`  
* `device_pixel_ratio`

These values are:

* Consistently available across browsers  
* Relatively stable over time  
* Sufficient to distinguish most displays in practice

This fingerprint is not guaranteed to be globally unique, but is **sufficiently discriminative within a device context**.

---

## **5\. Observation Model**

The system records observations of displays over time.

### **Observation Event**

Triggered on:

* Stable page load  
* Controlled intervals (optional, low frequency)

Each observation performs:

1. Capture current fingerprint  
2. Attempt to match existing display  
3. If matched:  
   * Increment `observation_count`  
   * Update `last_seen_at`  
4. If not matched:  
   * Create new display entry

---

## **6\. Display Stability**

Displays are treated as **probabilistic entities**.

A display becomes **stable** when:

observation\_count ≥ threshold (recommended: 5–10)

Before this threshold, displays are considered tentative.

This prevents:

* Noise from transient states  
* False positives from temporary configurations  
* Over-fragmentation of display records

---

## **7\. Multi-Display Detection**

A device is considered to have multiple displays when:

* Two or more displays reach stability

This condition implies:

> Repeated, consistent use of multiple distinct display configurations

---

## **8\. User Interaction Model**

### **8.1 Single-Display Case**

* No user interaction required  
* System operates silently  
* No display naming prompt

This covers the majority of users.

---

### **8.2 Multi-Display Case**

When multiple stable displays are detected:

The system may prompt:

> “We’ve noticed multiple screens. Would you like to name them?”

This interaction is:

* Optional  
* Non-blocking  
* Triggered only after confidence is established

---

### **8.3 Display Naming**

* Stored as `display_name`  
* Purely descriptive  
* No impact on system identity or matching

Examples:

* “Main screen”  
* “Left monitor”  
* “TV”

---

## **9\. Device vs Display Distinction**

The system distinguishes clearly between:

### **Device**

* Logical machine identity  
* User-defined and persistent  
* Example: “Ashley’s computer”

### **Display**

* Physical screen attached to device  
* System-inferred  
* May be multiple per device

Key principle:

Devices are declared  
Displays are inferred

---

## **10\. Design Principles**

### **10.1 Minimalism**

Only capture what is necessary:

* Avoid overfitting  
* Avoid noisy or unstable signals

---

### **10.2 Stability Over Precision**

Prefer:

* consistent behavior  
* gradual confidence

Over:

* exact but fragile detection

---

### **10.3 Deferred User Interaction**

Follow the pattern:

observe → infer → confirm

Avoid:

* early prompts  
* unnecessary configuration  
* user fatigue

---

### **10.4 Observational Authority**

The system does not assume correctness from a single event.

Instead:

* truth emerges from repeated observation  
* confidence increases over time

---

## **11\. Limitations**

* Cannot detect all displays unless used by the application  
* Cannot determine physical layout (left/right/top/bottom)  
* Cannot guarantee uniqueness across identical displays  
* Sensitive to rare changes in resolution or scaling

These limitations are accepted as part of the browser environment.

---

## **12\. Conclusion**

This model provides a practical, scalable approach to display identification in a constrained environment.

By relying on:

* lightweight fingerprints  
* repeated observation  
* confidence thresholds

the system achieves:

* low friction  
* high usability  
* sufficient accuracy for real-world applications

without requiring deep system access or complex configuration.
