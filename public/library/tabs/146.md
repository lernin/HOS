# Progressive ID

# **Progressive Device Identity & Safe Cross-Client Synchronization**

## **1\. Overview**

This system addresses a fundamental challenge in modern applications:

How to provide seamless cross-browser and cross-client continuity without compromising privacy or incorrectly identifying devices.

Rather than attempting to definitively identify devices at first contact, this model introduces a **progressive, confidence-based approach** that separates:

* **User identity (portable)**  
* **Client identity (certain)**  
* **Device identity (inferred and optional)**

---

## **2\. Core Principles**

### **2.1 Identity Separation**

User \= portable identity (via login or magic link)  
Client \= runtime instance (browser/app)  
Device \= inferred grouping of clients

Key rule:

**User identity can move freely. Device identity cannot.**

---

### **2.2 Default Safety**

All operations default to the safest possible behavior:

* No assumptions about device identity  
* No automatic sharing of local context  
* No exposure of other user profiles

---

### **2.3 Progressive Inference**

Device identity is not declared upfront. Instead:

observe → infer → confirm → unify

---

## **3\. Magic Link / Code-Based Identity Transfer**

### **3.1 Purpose**

Magic links (e.g., 6-digit codes or URLs) are used to:

Transfer **user identity only**, not device context

---

### **3.2 Behavior**

When a magic link is used:

* A new **client** is created  
* The **user is authenticated**  
* A **new or provisional device** is assigned  
* No device-level data is restored

Result:

Same user  
New client  
Untrusted device context

---

### **3.3 Security Boundary**

Magic links must NOT:

* Restore device rosters  
* Reveal other profiles  
* Implicitly trust the new environment

This prevents:

Unauthorized access to shared device contexts

---

## **4\. Device Inference Model**

### **4.1 Observational Signals**

The system collects weak signals such as:

* Screen width and height  
* Repeated usage patterns  
* Shared user identity across clients  
* Timing and behavior correlations

No single signal is authoritative.

---

### **4.2 Confidence Accumulation**

Over time, the system builds a **device confidence score** based on:

* Repeated co-occurrence of signals  
* Consistent user behavior across clients

---

### **4.3 Ambiguity Acceptance**

The system allows:

* Duplicate devices  
* Uncertain mappings  
* Parallel interpretations

Ambiguity is resolved only when meaningful.

---

## **5\. Delayed Device Unification**

### **5.1 Trigger Condition**

When confidence becomes sufficiently high:

* Multiple clients appear to belong to the same device  
* The same user is active across them

---

### **5.2 User Prompt**

The system asks:

“We believe these clients are on the same device. Would you like to sync them?”

---

### **5.3 User Action**

If confirmed:

* Clients are merged under a single device identity  
* Device-level context becomes shared  
* The experience becomes unified across browsers/apps

---

## **6\. Device Synchronization**

### **6.1 Behavior After Sync**

Once unified:

* Device roster is restored across clients  
* Profiles become visible across browsers  
* The experience feels consistent regardless of entry point

---

### **6.2 Scope Limitation**

Synchronization applies:

* Only within a confirmed device  
* Not across unrelated devices

---

## **7\. UX Philosophy**

### **7.1 Minimal Friction**

* No early prompts  
* No unnecessary questions  
* Silent operation by default

---

### **7.2 Meaningful Interaction Only**

User is engaged only when:

* The system has high confidence  
* The action provides clear value

---

### **7.3 User Control**

All major transitions (e.g., device unification) require:

* Explicit user confirmation  
* Clear intent

---

## **8\. System Behavior Summary**

### **Initial State**

Client created  
User optionally authenticated  
Device \= provisional  
No shared context

---

### **Observational Phase**

System collects signals  
Confidence increases over time  
No user interaction

---

### **Decision Point**

Confidence threshold reached  
User prompted for confirmation

---

### **Final State**

Clients unified under one device  
Device context shared  
Cross-browser continuity achieved

---

## **9\. Key Insight**

Seamless cross-browser experience should not come from early assumptions, but from **earned confidence and user confirmation**.

---

## **10\. Conclusion**

This model achieves:

* **Security by default**  
* **Seamless user experience over time**  
* **Accurate device grouping without overreach**

By delaying commitment and leveraging user confirmation, the system avoids both:

* premature assumptions  
* excessive friction

and instead delivers:

**Safe, intelligent, and adaptive identity continuity**
