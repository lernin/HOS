\#\# 1. Executive Summary

  

The Artifact Processing and Semantic Registration system transforms raw student language into concept-grounded educational evidence through a structured processing pipeline. The system simultaneously analyzes learner production, generates pedagogical evidence, maintains an evolving semantic knowledge base, and drives adaptive curriculum decisions.

  

\#\#\# Core Pipeline

  

\`\`\`

Artifact → Correction → Parsing → Lexical Resolution → Atomonym Assignment

                                                              ↓

                                                    Evidence Generation

                                                              ↓

                                                    Mastery Update

                                                              ↓

                                                    Curriculum Planning

\`\`\`

  

\#\#\# Lexical Resolution Strategy

  

For each word in the artifact, meaning is determined through staged lookup:

  

| Order | Source | Action |

|-------|--------|--------|

| 1 | Unambiguous Registry | Words with a dominant modern meaning are resolved immediately |

| 2 | Registered Term Registry | If multiple meanings exist, AI selects using context |

| 3 | New Meaning Creation | Unknown words are analyzed, and a new atomonym is created |

  

\#\#\# Key Innovation

  

Artifacts are analyzed as sequences of \*\*atomonyms\*\* — atomic meaning units that bind string, concept, grammar, and form. This ensures that evidence is based on \*meaning\*, not raw string matching.

  

\#\#\# Outcome

  

The pipeline produces:

\- Corrected text

\- Concept-grounded analysis

\- Semantic evidence

\- Mastery updates

\- Adaptive curriculum decisions

\- A continuously improving lexical knowledge system

\#\# 2. Core Concepts

  

\#\#\# 2.1 The Atomonym

  

An \*\*atomonym\*\* (atomic meaning unit) is the system's fundamental semantic building block. It binds four essential dimensions of linguistic information:

  

| Component | Description | Example |

|-----------|-------------|---------|

| \*\*String\*\* | The orthographic form | "ran" |

| \*\*Concept\*\* | The meaning, linked to other concepts | RUN (past tense) |

| \*\*Grammar\*\* | Part of speech, inflection, syntactic role | verb, past tense, intransitive |

| \*\*Form\*\* | Capitalization, spelling variant | lowercase, standard spelling |

  

\#\#\#\# Atomonym Properties

  

Each atomonym carries metadata essential for analysis:

  

\- \*\*Unique identifier\*\* (UUID) for referencing across the system

\- \*\*Confidence score\*\* (0.0-1.0) representing certainty of correct concept binding

\- \*\*Creation timestamp\*\* for tracking knowledge age

\- \*\*Source attribution\*\* (AI-created, verified, student-inferred, etc.)

\- \*\*Usage statistics\*\* (frequency, contexts, student associations)

  

\#\#\#\# Atomonym Example

  

\`\`\`json

{

    "atomonym\_id": "aton\_7893",

    "string": "potato",

    "concept": "POTATO",

    "grammar": {

        "pos": "noun",

        "number": "singular",

        "countability": "count"

    },

    "form": {

        "capitalization": "lowercase",

        "spelling": "standard"

    },

    "confidence": 0.99,

    "created": "2024-01-15",

    "source": "lexicon\_import"

}

\`\`\`

  

\#\#\# 2.2 The Lexical Registry

  

The lexical registry is a unified data structure mapping strings to their known meanings, with confidence scores representing completeness of knowledge.

  

\#\#\#\# Registry Entry Schema

  

\`\`\`json

{

    "string": "bat",

    "known\_atomonyms": \["aton\_2345", "aton\_2346"\],

    "completeness\_confidence": 0.85,

    "frequency\_band": 2,

    "last\_reviewed": "2024-02-15",

    "review\_count": 12,

    "etymology": { "origin": "Old English", "notes": "" },

    "usage\_notes": { "register": "neutral", "domain": null }

}

\`\`\`

  

| Field | Description |

|-------|-------------|

| \`string\` | The orthographic form (canonical spelling) |

| \`known\_atomonyms\` | List of atomonym IDs for this string |

| \`completeness\_confidence\` | How sure the system is that all meanings are known (0.0-1.0) |

| \`frequency\_band\` | 1-5 indicating corpus frequency tier |

| \`last\_reviewed\` | Timestamp of most recent semantic review |

| \`review\_count\` | Number of times this entry has been reviewed |

| \`etymology\` | Optional historical origin information |

| \`usage\_notes\` | Register, dialect, domain restrictions |

  

\#\#\#\# Frequency Banding

  

Based on Zipf's Law, words are organized into frequency bands for efficient lookup:

  

| Band | Word Ranks | Coverage | Review Priority |

|------|------------|----------|-----------------|

| \*\*Band 1\*\* | 1-100 | \~50% of all text | Highest |

| \*\*Band 2\*\* | 101-1,000 | \~72% total | High |

| \*\*Band 3\*\* | 1,001-2,000 | \~80% total | Medium |

| \*\*Band 4\*\* | 2,001-5,000 | \~86.7% total | Low |

| \*\*Band 5\*\* | 5,000+ | \~89% total | Lowest |

  

\#\#\#\# 2.2.1 Emergent Ambiguity Classification

  

The system does not store an "unambiguous" flag on words. Instead, ambiguity is an \*\*emergent property\*\* derived from registry data:

  

| Registry Pattern | Emergent Status |

|------------------|-----------------|

| One known atomonym + high completeness confidence | \*\*Practically unambiguous\*\* (safe for fast path) |

| Multiple known atomonyms + high completeness confidence | \*\*Fully mapped ambiguous\*\* (context needed) |

| One known atomonym + low completeness confidence | \*\*Potentially ambiguous\*\* (unknown unknowns) |

| Multiple known atomonyms + low completeness confidence | \*\*Incompletely mapped ambiguous\*\* (may have more) |

  

This design is more honest than storing "unambiguous" flags—it acknowledges that what we don't know about a word is as important as what we do know.

  

\#\#\# 2.3 Practical Unambiguity

  

The system distinguishes between \*\*absolute ambiguity\*\* and \*\*practical ambiguity\*\*. A word may have multiple meanings in the full history of language but still be \*\*practically unambiguous\*\* in modern natural language when one dominant meaning overwhelmingly accounts for normal use.

  

Example: \*forest\* has rare historical meanings (royal hunting reserve) and technical meanings (to forest land), but in modern natural language it overwhelmingly means "wooded area." It can be treated as practically unambiguous.

\#\# 4. Stage 1: Artifact Ingestion

  

\#\#\# Definition

  

An \*\*artifact\*\* is any student-produced language sample submitted to the system for analysis.

  

\#\#\# Artifact Types

  

| Type | Description | Examples |

|------|-------------|----------|

| \*\*Sentence\*\* | Single independent clause | "I ate a potato." |

| \*\*Paragraph\*\* | Multiple related sentences | Short journal entry |

| \*\*Essay\*\* | Extended composition | Multi-paragraph assignment |

| \*\*Short answer\*\* | Brief response to prompt | "The main character was sad because..." |

| \*\*Transcribed speech\*\* | Spoken language converted to text | Oral reading, dictation |

| \*\*Dialogue\*\* | Conversational exchange | Chat with tutor, peer discussion |

  

\#\#\# Ingestion Requirements

  

For each artifact, the system stores:

  

| Field | Description | Example |

|-------|-------------|---------|

| \`artifact\_id\` | Unique identifier | "art\_20240315\_001" |

| \`student\_id\` | Learner identifier | "student\_789" |

| \`timestamp\` | Submission time | "2024-03-15T14:32:10Z" |

| \`raw\_text\` | Exact student input | "I eated a potate yesturday." |

| \`context\` | Assignment/prompt info | "Journal entry about yesterday's meal" |

| \`artifact\_type\` | Sentence/paragraph/essay/etc. | "sentence" |

  

\#\#\# Design Principle: Authoritative Source

  

The original artifact remains \*\*unchanged and permanently stored\*\*. All downstream processing references but never modifies the raw artifact. This ensures auditability, allows reprocessing with improved algorithms, and preserves the complete historical record.

\#\# 5. Stage 2: AI Correction Pass

  

\#\#\# Purpose

  

The correction pass identifies and documents discrepancies between what the student wrote and standard written English, producing two parallel outputs: a corrected version for semantic processing and a detailed set of correction notes for evidence generation.

  

\#\#\# Correction Types

  

| Error Category | Subtypes | Example |

|----------------|----------|---------|

| \*\*Spelling\*\* | Phonetic, visual, homophone | "potate" → "potato" |

| \*\*Capitalization\*\* | Sentence start, proper nouns | "i ate" → "I ate" |

| \*\*Punctuation\*\* | Missing, incorrect, extraneous | "I ate potato" → "I ate potato." |

| \*\*Grammar\*\* | Verb tense, agreement, article usage | "I eated" → "I ate" |

| \*\*Word choice\*\* | Incorrect word for context | "consumed" → "ate" (register) |

| \*\*Word order\*\* | Syntactic misordering | "Potato I ate" → "I ate potato" |

  

\#\#\# Correction Notes Structure

  

\`\`\`json

{

    "correction\_id": "corr\_001",

    "artifact\_id": "art\_20240315\_001",

    "original\_span": { "start": 2, "end": 7, "text": "eated" },

    "corrected\_span": { "start": 2, "end": 5, "text": "ate" },

    "error\_type": "grammar",

    "subtype": "verb\_tense",

    "description": "Irregular verb 'eat' past tense should be 'ate'",

    "confidence": 0.98,

    "alternatives": \[\]

}

\`\`\`

  

\#\#\# Correction Outputs

  

The correction pass produces:

1\. \*\*Corrected text\*\* — a clean version for semantic processing

2\. \*\*Correction notes array\*\* — all identified issues

3\. \*\*Diagnostic metadata\*\* — readability score, error density, pattern flags

\#\# 6. Stage 3: Structural Extraction (Parsing)

  

\#\#\# Purpose

  

The corrected text is parsed into hierarchical structural components, enabling analysis at multiple granularities: whole artifact, paragraphs, sentences, expressions (phrases), and words.

  

\#\#\# STAX Model

  

The system employs the STAX (Structural Taxonomy) model:

  

| Level | STAX Term | Definition | Example |

|-------|-----------|------------|---------|

| Word | \*\*Atom\*\* | Smallest meaningful unit | "potato", "ate", "the" |

| Phrase | \*\*Functional\*\* | Group of atoms functioning as unit | "the potato", "ate quickly" |

| Simple sentence | \*\*Molecule\*\* | Independent clause | "I ate a potato." |

| Repeated structures | \*\*Polymer\*\* | Coordinated similar units | "I ate and ran." |

| Combined structures | \*\*Composite\*\* | Subordination/different structures | "I ate because I was hungry." |

| Unordered collections | \*\*Mixture\*\* | Loosely related elements | List, fragmented thought |

  

A sentence may be classified as a molecule, polymer, composite, or mixture depending on its internal structure. This classification enables granular analysis of syntactic development.

{

    "artifact\_id": "art\_20240315\_001",

    "structure": {

        "type": "molecule",

        "text": "I ate a potato yesterday.",

                "text": "I",

                "atoms": \["I"\]

            {

                "type": "functional",

                "text": "ate a potato",

\#\# 7. Stage 4: Lexical Resolution

  

\#\#\# Purpose

  

Lexical resolution determines the meaning (concept) for each word in the corrected artifact by consulting the lexical registry and applying contextual reasoning.

  

\#\#\# Resolution Flow

  

\`\`\`

For each word in corrected artifact:

  

    ┌─────────────────────────────────────┐

    │ Look up word string in registry      │

    └─────────────────────────────────────┘

                      │

        ┌─────────────┴─────────────┐

        │                           │

        ▼                           ▼

   ┌───────────┐             ┌───────────────┐

   │ Found?    │───No───────▶│ Create new    │

   └───────────┘             │ entry         │

        │                    │ (initialized) │

        │ Yes                └───────┬───────┘

        ▼                            │

   ┌───────────┐                      │

   │ Check     │                      │

   │ known     │                      │

   │ atomonyms │                      │

   └─────┬─────┘                      │

         │                            │

         ▼                            │

   ┌───────────┐                      │

   │ How many  │                      │

   │ atomonyms?│                      │

   └─────┬─────┘                      │

         │                            │

    ┌────┴────┬───────────┐           │

    ▼         ▼           ▼           │

┌───────┐ ┌───────┐ ┌───────────┐    │

│ One   │ │Multiple││Zero (new) │────┘

└───┬───┘ └───┬───┘ └───────────┘

    │         │

    │         │ Use AI context

    │         │ to select best

    │         ▼

    │    ┌───────────┐

    │    │Selected   │

    │    │atomonym   │

    │    └─────┬─────┘

    └──────────┴──────────┘

              │

              ▼

    ┌─────────────────────┐

    │ Assign atomonym to   │

    │ word in analysis    │

    └─────────────────────┘

\`\`\`

  

\#\#\# Resolution Cases

  

| Case | Action | Rationale |

|------|--------|----------|

| \*\*One atomonym, high completeness\*\* | Assign immediately | Word is effectively unambiguous |

| \*\*Multiple atomonyms, high completeness\*\* | AI selects using context | Word is ambiguous but fully mapped |

| \*\*One atomonym, low completeness\*\* | Assign, flag for review | May have missing meanings |

| \*\*Multiple atomonyms, low completeness\*\* | AI selects, intensive review | Incomplete knowledge of ambiguous word |

| \*\*Word not found\*\* | Create new entry (initialized) | New vocabulary encountered |

  

\#\#\# Context-Based Selection Algorithm

  

When multiple atomonyms exist, the system uses:

1\. \*\*Local context\*\* — surrounding words and their atomonyms

2\. \*\*Syntactic role\*\* — subject, object, modifier, etc.

3\. \*\*Semantic compatibility\*\* — does this meaning fit the sentence?

4\. \*\*Collocation patterns\*\* — common word combinations

5\. \*\*Student history\*\* — has this student used this word before?

\#\# 9. Stage 6: Evidence Generation

  

\#\#\# The Critical Integration

  

Evidence generation is where the two parallel tracks—correction and semantic resolution—finally merge. This produces evidence that is simultaneously grounded in meaning and sensitive to actual production.

  

\#\#\# Merge Process

  

For each position in the artifact, the system combines:

  

| Source | Information Provided |

|--------|---------------------|

| \*\*Atomonym sequence\*\* | What concept the student intended |

| \*\*Correction notes\*\* | What the student actually wrote and what was wrong |

| \*\*Original artifact\*\* | The raw text for reference |

  

\#\#\# Evidence Templates

  

| Case | Original | Corrected | Atomonyms | Evidence |

|------|----------|-----------|-----------|----------|

| \*\*Correct usage\*\* | "I ate potato" | "I ate potato" | \[I, EAT, POTATO\] | Concepts confirmed |

| \*\*Spelling only\*\* | "I ate potate" | "I ate potato" | \[I, EAT, POTATO\] | Concept confirmed; spelling needs work |

| \*\*Grammar + spelling\*\* | "I eated a potate" | "I ate a potato" | \[I, EAT, POTATO\] | Concepts confirmed; grammar and spelling need work |

| \*\*Word choice\*\* | "I consumed a potato" | "I ate a potato" | \[I, EAT, POTATO\] | Concepts confirmed; register needs work |

| \*\*Concept confusion\*\* | "I ate a tomato" (but context was potato) | "I ate a potato" | \[I, EAT, POTATO\] | Possible concept confusion |

  

\#\#\# Evidence Structure

  

\`\`\`json

{

    "evidence\_id": "ev\_20240315\_001\_003",

    "artifact\_id": "art\_20240315\_001",

    "student\_id": "student\_789",

    "evidence\_type": "vocabulary\_usage",

    "concept\_id": "POTATO",

    "atomonym\_id": "aton\_7893",

    "demonstration": {

        "attempted": true,

        "correct": false,

        "error\_type": "spelling",

        "error\_subtype": "phonetic",

        "original\_form": "potate",

        "corrected\_form": "potato"

    },

    "mastery\_impact": {

        "concept\_confidence\_delta": +0.05,

        "skill\_delta": { "spelling\_potato": -0.1 }

    }

}

\`\`\`

  

\#\#\# Evidence Categories

  

| Category | Subcategories |

|----------|---------------|

| \*\*Vocabulary\*\* | Correct use, incorrect use, concept confusion, register error |

| \*\*Grammar\*\* | Tense, aspect, agreement, word order, article use, preposition use |

| \*\*Syntax\*\* | Sentence completeness, clause structure, subordination |

| \*\*Mechanics\*\* | Spelling, capitalization, punctuation |

| \*\*Pragmatics\*\* | Register, coherence, cohesion, audience awareness |

\#\# 10. Stage 7: Mastery Update

  

\#\#\# Purpose

  

The mastery profile maintains a dynamic model of each student's demonstrated knowledge and gaps across all language dimensions.

  

\#\#\# Mastery Data Structure

  

\`\`\`json

{

    "student\_id": "student\_789",

    "last\_updated": "2024-03-15T14:32:10Z",

    "concepts": {

        "POTATO": {

            "confidence": 0.85,

            "first\_evidence": "2024-02-01",

            "last\_evidence": "2024-03-15",

            "evidence\_count": 12,

            "correct\_count": 11,

            "error\_patterns": \["spelling"\]

        },

        "EAT": {

            "confidence": 0.92,

            "first\_evidence": "2024-01-15",

            "last\_evidence": "2024-03-15",

            "evidence\_count": 24,

            "correct\_count": 22,

            "error\_patterns": \["past\_tense\_irregular"\]

        }

    },

    "grammar\_patterns": {

        "past\_tense\_regular": { "confidence": 0.95 },

        "past\_tense\_irregular": { "confidence": 0.65 },

        "subject\_verb\_agreement": { "confidence": 0.88 }

    },

    "mechanics": {

        "capitalization\_sentence\_start": { "confidence": 0.97 },

        "spelling\_potato\_pattern": { "confidence": 0.70 }

    }

}

\`\`\`

  

\#\#\# Mastery Update Algorithm

  

For each evidence record:

  

1\. \*\*Identify affected concepts/skills\*\*

2\. \*\*Apply confidence delta\*\* based on:

   - Correctness (positive vs. negative evidence)

   - Recency (newer evidence weighted more)

   - Consistency (pattern across multiple attempts)

3\. \*\*Update error patterns\*\* (track specific recurring issues)

4\. \*\*Recalculate global metrics\*\*

5\. \*\*Trigger curriculum review\*\* if thresholds crossed

  

\#\#\# Confidence Decay (Forgetting Model)

  

To model forgetting, confidence slowly decays over time without reinforcement:

  

\`\`\`

daily\_decay\_rate = 0.001   \# 0.1% per day

monthly\_decay = 0.03       \# \~3% per month

\`\`\`

  

After 30 days without evidence for a concept:

  

\`\`\`

new\_confidence = original\_confidence × (1 - monthly\_decay)

\`\`\`

  

For example, a concept with confidence 0.90 that receives no reinforcement for 30 days would decay to:

  

\`\`\`

0.90 × 0.97 = 0.873

\`\`\`

  

This decay mechanism ensures that the mastery profile reflects not only what a student has demonstrated but also how recently they demonstrated it. Concepts that have been mastered but not used may require review.

\#\# 11. Stage 8: Curriculum Planning

  

\#\#\# Purpose

  

Based on the mastery profile, the curriculum system determines what the student should practice next, generating a prioritized queue of learning targets and assembling them into missions.

  

\#\#\# Key Distinctions

  

| Term | Definition | Example |

|------|------------|---------|

| \*\*Gap\*\* | A concept/skill with low confidence | Past tense of irregular verbs |

| \*\*Target\*\* | A specific item to practice | Form "ate" correctly |

| \*\*Queue\*\* | Prioritized list of targets | \[ate, gave, went, saw\] |

| \*\*Mission\*\* | Learning activity with one or more targets | "Practice irregular past tense: eat/give/go/see" |

  

\#\#\# Queue Generation Algorithm

  

The queue is populated and prioritized using:

  

1\. \*\*Gap severity\*\* (confidence deficit)

2\. \*\*Prerequisite relationships\*\* (can't do compound sentences before simple)

3\. \*\*Logical progression\*\* (present → past → perfect)

4\. \*\*Spaced repetition\*\* (items due for review)

5\. \*\*Student engagement\*\* (preferred topics, recent interests)

6\. \*\*Curriculum standards\*\* (if aligned with external requirements)

  

\#\#\# Example Queue Generation

  

\`\`\`

Student profile:

\- Can form simple present: "I eat" (confidence 0.95)

\- Can form simple past regular: "I walked" (confidence 0.90)

\- Struggles with irregular past: "I eated" (confidence 0.60)

\- Has concept POTATO (confidence 0.85) but misspells it

  

Queue priority:

1\. Target: Irregular past "ate" (gap severity: high)

2\. Target: Irregular past "gave" (logical next after "ate")

3\. Target: Spelling pattern "-ato" (potato, tomato) (secondary gap)

4\. Review: Regular past tense (spaced repetition)

5\. Preview: Present perfect "have eaten" (logical progression)

\`\`\`

  

\#\#\# Mission Assembly

  

Missions group compatible targets into coherent activities:

\#\# 12. Background Semantic Governance

  

\#\#\# Purpose

  

The semantic governance system operates continuously in the background, reviewing and refining the lexical registry. Its goals:

  

\- Improve completeness confidence for all words

\- Discover missing meanings

\- Validate or correct existing atomonyms

\- Promote well-understood words to higher confidence tiers

\- Demote words when new ambiguity is discovered

\- Maintain the overall health and accuracy of the semantic knowledge base

  

\#\#\# New Atomonym Lifecycle

  

When a new atomonym is created, it is not assumed to be fully settled. It begins with a lifecycle state:

  

| Status | Meaning |

|--------|---------|

| \*\*Initialized\*\* | Newly created; not yet reviewed |

| \*\*Provisional\*\* | Under review; confidence low |

| \*\*Reviewed\*\* | Has passed initial review |

| \*\*Stable\*\* | Well-understood; high confidence |

| \*\*Disputed\*\* | Conflicting evidence about meaning |

\#\#\# Meaning Classification

  

Each meaning associated with a word can be classified by usage type:

  

| Classification | Description | Example (forest) |

|----------------|-------------|------------------|

| \*\*Modern\*\* | Current, dominant usage | wooded area |

| \*\*Rare\*\* | Infrequent but current | to forest land |

| \*\*Technical\*\* | Specialist domain only | forestry management |

| \*\*Historical\*\* | No longer current | royal hunting reserve |

| \*\*Obsolete\*\* | No longer used | — |

  

\#\#\# Practical Unambiguity Decision

  

A word is treated as \*\*practically unambiguous\*\* when one dominant meaning overwhelmingly accounts for normal use in modern natural language. This allows the system to skip disambiguation for ordinary cases while still preserving secondary meanings in the registry.

  

Example: \*forest\* is practically unambiguous even though rare and historical meanings exist.

  

If review later discovers that a supposedly unambiguous term is actually more ambiguous than expected, that word may be removed from the unambiguous registry and retained only in the broader registry.

  

\#\#\# Registry Refinement

  

The background governance process continuously:

  

\- \*\*Re-evaluates\*\* terms with low completeness confidence

\- \*\*Searches for\*\* missing meanings in high-frequency words

\- \*\*Updates\*\* frequency bands based on usage

\- \*\*Reclassifies\*\* words as their usage patterns become clearer

\- \*\*Promotes\*\* practically unambiguous words to fast lookup

\- \*\*Demotes\*\* words when new ambiguity is discovered

\# Appendix C: Supplemental Concepts — Addendum to Version 2.1

  

This addendum documents three significant concepts present in the foundational specifications that are not fully captured in Version 2.1. These concepts are essential for complete system understanding and implementation.

  

\---

  

\#\# C.1 The Initialized Lifecycle State and Governance Trigger

  

\#\#\# C.1.1 Concept

  

When a new atomonym is created (because a word was not found in the registry), it is \*\*not\*\* assumed to be settled or accurate. Instead, it enters the system with a provisional status that signals it requires background review. This is the mechanism that enables the system to use new terms immediately while maintaining long-term accuracy through continuous refinement.

  

\#\#\# C.1.2 New Atomonym Lifecycle

  

| Status | Meaning | Action |

|--------|---------|--------|

| \*\*Initialized\*\* | Newly created; not yet reviewed | Immediately usable for analysis; flagged for governance queue |

| \*\*Provisional\*\* | Under active review; confidence low | Background analysis in progress; may be promoted or revised |

| \*\*Reviewed\*\* | Has passed initial review | Ready for normal use; confidence increased |

| \*\*Stable\*\* | Well-understood; high confidence | No routine review needed; may be considered for unambiguous registry |

| \*\*Disputed\*\* | Conflicting evidence about meaning | Requires human review or additional corpus analysis |

  

\#\#\# C.1.3 Creation Flow

  

When a word is not found in the registry:

  

1\. AI infers meaning from context (typically through Hypernym relationships)

2\. System creates new concept (if needed) or links to existing concept

3\. System mints a new atomonym binding string to concept

4\. New registry entry is created with:

   - \`status: "initialized"\`

   - \`completeness\_confidence\`: low (e.g., 0.3–0.5)

   - \`known\_atomonyms\`: \[new atomonym ID\]

5\. Entry is \*\*immediately usable\*\* for the current artifact analysis

6\. Entry is \*\*automatically queued\*\* for background semantic governance

  

\#\#\# C.1.4 Integration with Background Governance

  

The background semantic governance system (Section 12 of the main document) consumes entries with status \`initialized\` (and \`provisional\`) as its primary input. The governance pipeline then:

  

\- Evaluates whether additional meanings exist

\- Determines modern usage frequency

\- Classifies each meaning (modern / rare / technical / historical / obsolete)

\- Decides practical unambiguity status

\- Promotes or demotes the entry accordingly

\- Updates status to \`reviewed\`, \`stable\`, or \`disputed\`

  

Without the \`initialized\` status as a trigger, the governance system has no systematic way to identify which entries require review.

\#\# C.2 Frequency-Banded Lookup Optimization

  

\#\#\# C.2.1 Concept

  

To optimize lookup performance, the lexical registry is searched in frequency band order, not as a single flat structure. This recognizes that the most common words account for the majority of text and should be found fastest.

  

\#\#\# C.2.2 Frequency Band Structure

  

Based on Zipf's Law and corpus linguistics:

  

| Band | Word Ranks | Cumulative Coverage | Lookup Priority |

|------|------------|---------------------|-----------------|

| \*\*Band 1\*\* | 1–100 | \~50% of all text | First |

| \*\*Band 2\*\* | 101–1,000 | \~72% total | Second |

| \*\*Band 3\*\* | 1,001–2,000 | \~80% total | Third |

| \*\*Band 4\*\* | 2,001–5,000 | \~86.7% total | Fourth |

| \*\*Band 5\*\* | 5,000+ | \~89% total | Fifth |

  

\#\#\# C.2.3 Banded Search Algorithm

  

During lexical resolution (Stage 4 of the main pipeline), for each word:

  

\`\`\`

1\. Search Band 1 (ranks 1–100)

   → If found, retrieve atomonym(s) and proceed to disambiguation if needed

  

2\. If not found in Band 1, search Band 2 (ranks 101–1,000)

  

3\. If not found in Band 2, search Band 3 (ranks 1,001–2,000)

  

4\. If not found in Band 3, search Band 4 (ranks 2,001–5,000)

  

5\. If not found in Band 4, search Band 5 (ranks 5,000+)

  

6\. If not found in any band, proceed to new meaning creation

\`\`\`

  

\#\#\# C.2.4 Performance Rationale

  

Because Band 1 covers 50% of all text, the majority of word lookups complete after a single, small-index search. This design is more efficient than:

\- Searching a single large index for every word

\- Applying frequency-based ranking after retrieval

  

\#\#\# C.2.5 Relationship to Unambiguous Registry

  

The unambiguous registry (practically unambiguous words) may be implemented as a subset of Band 1 and Band 2, or as a separate fast-path lookup that precedes banded search. Either implementation preserves the optimization principle.

\#\# C.3 STAX Model: Detailed Polymer, Composite, and Mixture Distinctions

  

\#\#\# C.3.1 Concept

  

The STAX (Structural Taxonomy) model distinguishes multiple sentence-level structures beyond the simple sentence (molecule). These distinctions are critical for tracking syntactic development, as they represent increasingly complex language production.

  

\#\#\# C.3.2 Complete STAX Hierarchy

  

| Level | STAX Term | Definition | Developmental Significance |

|-------|-----------|------------|---------------------------|

| Word | \*\*Atom\*\* | Smallest meaningful unit | Foundational vocabulary |

| Phrase | \*\*Functional\*\* | Group of atoms functioning as unit | Basic modification and argument structure |

| Simple sentence | \*\*Molecule\*\* | Single independent clause | Core clause production |

| Repeated structures | \*\*Polymer\*\* | Coordinated similar units (and/or) | Conjunction use, list construction |

| Combined structures | \*\*Composite\*\* | Subordination or different structures (because, if, when) | Complex syntax, clause embedding |

| Unordered collections | \*\*Mixture\*\* | Loosely related elements (lists, fragments) | Informal discourse, brainstorming |

\#\#\# C.3.4 Why These Distinctions Matter

  

| Structure | Indicates | Next Developmental Target |

|-----------|-----------|--------------------------|

| Molecule only | Basic clause production | Coordination (and/or) |

| Polymer | Conjunction use, list construction | Subordination (because, when, if) |

| Composite | Subordination, clause embedding | Multiple embedding, relative clauses |

| Mixture | Informal or early writing | Cohesive discourse, paragraph structure |

  

The system tracks which structures a student produces (and produces correctly) to identify the next appropriate syntactic target. A student who reliably produces molecules but never polymers needs practice with coordination. A student who produces polymers but struggles with composites needs practice with subordination.
